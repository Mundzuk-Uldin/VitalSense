# VitalSense

An Apple Watch reads your vitals, a fastai model scores how sick you look,
and your iPhone shows you the answer and the reasoning behind it.

**Everything runs on the device.** The trained model is a 17 KB Core ML graph
in the app bundle — no server, no network request, no account. Readings never
leave your wrist and your phone.

| Piece | What it does |
|---|---|
| `model/` | Trains a fastai tabular model on `Health_Risk_Dataset.csv` and exports it to Core ML |
| `app/VitalSenseWatch/` | watchOS app: reads the sensors, scores on the watch, shows the band |
| `app/VitalSense/` | iOS app: fills in what the watch cannot measure, and shows the full result |

> **Not a medical device.** This is a demonstration built on a synthetic
> dataset. Nothing here should inform a care decision.

---

## 1. The model

The dataset is 1,000 rows of NEWS2 (National Early Warning Score 2)
observations — respiratory rate, SpO₂, oxygen scale, systolic BP, heart rate,
temperature, consciousness (ACVPU) and supplemental oxygen — labelled
`Normal` / `Low` / `Medium` / `High`.

```bash
python3 -m venv .venv                      # Python 3.11+; built on Homebrew's 3.14
.venv/bin/pip install -r model/requirements.txt
.venv/bin/python model/train.py
```

A fastai `tabular_learner` — two hidden layers of 64 and 32, an embedding for
the one categorical column, 30 epochs of one-cycle.

| Held-out (200 rows) | |
|---|---|
| accuracy | 0.995 |
| macro-F1 | 0.995 |
| mean bands off | 0.005 |

That last row matters more than accuracy. Mistaking Normal for High and
mistaking Low for Medium are both "one error", and they are nothing alike
clinically. The single held-out mistake is one Low scored as Medium.

### Why the score is so high, honestly

Because the labels are **generated by a rule**, not observed in the wild. The
published NEWS2 banding alone reproduces 987 of the 1,000 labels. The
remaining 13 are cases where three vitals are mildly abnormal but the
aggregate is still low — this dataset calls those `Medium` where the textbook
says `Low`. That extra rule is what the network learns and the rulebook does
not.

The model also gets three NEWS2-derived inputs (the aggregate, the worst
single component, and how many vitals are abnormal) alongside the seven raw
vitals. The apps compute those anyway in order to explain a result, so they
cost nothing at inference, and they save the network from rediscovering the
clinical cut-points from a thousand rows.

Treat the accuracy as evidence the pipeline is wired up correctly, not as
evidence the model would generalise to real patients.

### What training produces

```
model/artifacts/
├── VitalRisk.mlmodel   17 KB Core ML graph — also copied to app/Shared/
├── metadata.json       architecture, class order, normalisation stats, metrics
└── reference.json      24 frozen PyTorch predictions, for the Swift check
```

Normalisation is **baked into the exported graph**, so Swift passes raw
vitals. Ten means and ten standard deviations copied by hand into another
language is exactly the kind of thing that silently drifts, and a drifted
normaliser does not crash — it just quietly makes the model wrong.

`train.py` copies the model into `app/Shared/` itself, so retraining and
rebuilding the apps is one command rather than two plus a copy someone
forgets.

### Risk factors, not just a label

A neural network cannot tell a nurse *why*. NEWS2 can, so it runs alongside
the model purely as the explainability layer: one sub-score per vital, sorted
by severity, each with a plain-English note. That is what the apps render,
and it is ported to Swift in `app/Shared/NEWS2.swift`.

## 2. The apps

```bash
open app/VitalSense.xcodeproj
```

Two targets, one shared source folder:

```
app/
├── Shared/              compiled into both targets
│   ├── VitalsReading.swift   the reading, and where each number came from
│   ├── NEWS2.swift           the scoring rulebook, ported from Python
│   ├── RiskScorer.swift      Core ML inference
│   ├── RiskPrediction.swift  what the model said
│   ├── RiskPalette.swift     the four risk colours
│   ├── VitalRisk.mlmodel     the trained model
│   └── …
├── VitalSenseWatch/     watchOS 11+
└── VitalSense/          iOS 18+
```

The project is generated, not hand-maintained — add a `.swift` file to a
target folder and re-run:

```bash
python3 app/tools/generate_xcodeproj.py
```

### Checking it works without a wrist

Swift builds the model's ten-element feature vector by hand. If that order
ever drifts from `model/train.py`, nothing crashes — the model just returns
confident, wrong answers. So `tools/check_model.sh` compiles the shared Swift
for macOS, compiles the `.mlmodel`, and replays the frozen PyTorch
predictions through the real scorer:

```bash
app/tools/check_model.sh
```

It checks that all 24 reference labels match PyTorch and that the
probabilities agree to within 1e-4 (they currently agree to 6e-7), that the
Swift NEWS2 port reproduces the Python one, that SpO₂ scale 2 tolerates a
lower saturation than scale 1, and that worse vitals never score lower.

`--seed-simulator` pushes a three-reading history into a booted iOS
Simulator, so the results screens render with genuine on-device predictions.

### What the watch can actually measure

This is the part that shapes the whole design. An Apple Watch Series 9
(A2984) covers four of NEWS2's seven vitals, each on its own schedule:

| Vital | Availability |
|---|---|
| Heart rate | Continuous. The app starts an `HKWorkoutSession` to raise sampling from every few minutes to roughly 1 Hz |
| Blood oxygen | Background sampling at rest — **and disabled outright on units sold in the US after January 2024** |
| Respiratory rate | Derived during sleep only |
| Wrist temperature | Derived during sleep only |
| Systolic BP | Not measurable by any Apple Watch |
| Consciousness (ACVPU) | Not measurable |
| Supplemental oxygen | Not measurable |

So the apps never pretend. Every vital carries a **provenance** —
`sensor`, `manual`, or `assumed` — and the iPhone shows it: "3 of 4
measured", "Assumed normal: blood oxygen", "Measured 4 minutes ago". A
"Normal" verdict built on four assumptions is visibly that.

The three unmeasurable vitals live on the iPhone's **Other vitals** sheet.
Blood pressure matters most — a systolic under 90 is three points on its own
— so leaving it silently at 120 would flatter every reading. Changing
anything there re-scores the latest reading and pushes the new result back to
the watch.

### Wrist temperature is not body temperature

`appleSleepingWristTemperature` is skin temperature at the wrist: roughly
33–35 °C in a healthy person. Fed straight into NEWS2 that scores 3 points
for hypothermia on someone who is perfectly well. Apple's own Health app
never shows the absolute value either — it shows a *deviation* from your
personal baseline.

So `VitalsCollector.estimatedBodyTemperature()`:

1. Uses a real `bodyTemperature` sample if one was logged in the last 12 hours.
2. Otherwise averages the last 30 days of wrist readings into a baseline,
   takes tonight's deviation from it (clamped to ±3 °C, because a wider swing
   is a loose band or a cold room), and applies that to a normal 37.0 °C.
3. With fewer than three nights of data, returns nothing — the reading keeps
   its assumed value and is flagged `assumed` rather than inventing a fever.

### How a reading travels

```
Apple Watch                              iPhone
  sensors ──► reading ──► Core ML ──► band on wrist
                              │
                              └── reading + score ──WC──► history, detail
                                                          (re-scores on its
                                                           own Core ML when
                                                           you edit the
                                                           manual vitals)
```

Both devices carry the same model, so the watch scores its own reading and
shows the band immediately — no round trip, no dependency on the phone being
in range. The phone is told afterwards, by `sendMessage` when it is listening
and `transferUserInfo` when it is not, so the history fills in either way.

### On screen

**iPhone** — three tabs. *Now* answers three questions in order: the verdict
(band, NEWS2 total, recommendation), what the watch actually measured (four
tiles with provenance), and what is driving it (contributing vitals with
severity and points), then the model's confidence across all four bands.
*History* keeps the last 100 readings, including ones that failed to score,
with the reason. *Settings* shows the model state and the watch link.

**Watch** — three vertical pages: the result as a hero readout, the live
vitals with their provenance, and controls (start/stop monitoring, plus demo
readings). No chart; the screen is too small for one to be honest.

### No watch? No problem

Both apps have a demo path that runs a plausible reading through the real
model. iOS: Settings → *Score a demo reading*, or the button on the empty
state. watchOS: the Controls page. Demo readings are tagged `source: "demo"`
so nothing downstream mistakes them for measurements.

### Colour

The four bands use a reserved status palette — good, warning, serious,
critical — that never doubles as a series colour. Two of the four sit below
3:1 contrast on a light surface by design, so the mitigation is structural:
a band never appears without its SF Symbol **and** its written name, and
every severity is spelled out ("Moderate · 2 points") next to its colour.
Colour alone never carries meaning anywhere in either app.

## Running it on your own devices

There is nothing to run first and nothing to configure. The model ships
inside the app.

### 1. Make the project yours to sign

Bundle IDs are globally unique to Apple, so two people cannot both ship
`com.bayhacks.VitalSense`. In Xcode, for **each** of the two targets →
Signing & Capabilities:

- Tick **Automatically manage signing** and pick your Team (a free Apple ID is fine)
- iOS target bundle ID → `com.yourname.VitalSense`
- Watch target bundle ID → `com.yourname.VitalSense.watchkitapp`

The watch ID must be the iOS ID plus `.watchkitapp`, or the watch app will
not install. Then edit `app/VitalSenseWatch/Info.plist` and set
`WKCompanionAppBundleIdentifier` to your new iOS bundle ID — that one is not
automatic.

Add the **HealthKit** capability to the *watch* target only (+ Capability →
HealthKit). The iPhone app never touches HealthKit.

> These edits are personal to your machine. Please don't commit them to
> `main` — they would break everyone else's signing. `git update-index
> --skip-worktree app/VitalSense.xcodeproj/project.pbxproj` after you have
> them set is the easy way to stop them showing up in `git status`.

> Re-running `tools/generate_xcodeproj.py` rebuilds the project from
> scratch and **wipes your signing settings and the HealthKit entitlement**.
> Only run it if you add new Swift files.

### 2. Trust the hardware

- iPhone: connect by USB, unlock, tap **Trust**. Then Settings → Privacy &
  Security → **Developer Mode** → on (the phone reboots).
- Apple Watch: Settings → Privacy & Security → Developer Mode → on, reboot,
  and keep it unlocked on your wrist.

### 3. Build

Scheme **VitalSense** → your iPhone as destination → ⌘R. The watch app is
embedded in the iPhone app and installs with it; if it does not appear within
a minute, iPhone → Watch app → VitalSense → **Install**.

On the watch: Controls → **Start monitoring**, grant Health access, then
Result → **Read & Score**.

### What to expect on a real wrist

Probably "3 of 4 measured", with blood oxygen showing *Assumed normal*. That
is not a bug — see the sensor table above. Respiratory rate and wrist
temperature are sleep-derived, so a watch you only put on this morning has
neither yet. The watch's Controls page has demo readings that exercise the
real model end to end if you need to show the whole thing working
immediately.
