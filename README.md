# VitalSense

An Apple Watch reads your vitals, a model scores how sick you look, and your
iPhone shows you the answer and the reasoning behind it.

Three pieces:

| Piece | What it does |
|---|---|
| `backend/` | Trains a classifier on `Health_Risk_Dataset.csv` and serves it over FastAPI |
| `app/VitalSenseWatch/` | watchOS app: reads Apple Watch sensors, asks for a score, shows the band |
| `app/VitalSense/` | iOS app: fills in what the watch cannot measure, calls the model, shows the full result |

> **Not a medical device.** This is a demonstration built on a synthetic
> dataset. Nothing here should inform a care decision.

---

## 1. The model

The dataset is 1,000 rows of NEWS2 (National Early Warning Score 2)
observations — respiratory rate, SpO₂, oxygen scale, systolic BP, heart rate,
temperature, consciousness (ACVPU) and supplemental oxygen — labelled
`Normal` / `Low` / `Medium` / `High`.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
cd backend && python train.py
```

`train.py` cross-validates three candidates and keeps the best:

| Model | CV macro-F1 |
|---|---|
| Logistic regression | 0.988 |
| Random forest | 0.996 |
| **Histogram gradient boosting** | **1.000** |

Held-out (20%): accuracy 1.000, macro-F1 1.000, mean bands off 0.000.

### Why the score is perfect, honestly

Because the labels are **generated by a rule**, not observed in the wild. The
published NEWS2 banding alone reproduces 987 of the 1,000 labels. The
remaining 13 are all cases where three vitals are mildly abnormal but the
aggregate is still low — this dataset calls those `Medium` where the textbook
says `Low`. That extra rule is exactly what the model learns and the rulebook
does not.

The features make the difference visible:

| Features | CV macro-F1 |
|---|---|
| Raw vitals only | 0.961 |
| Raw vitals + NEWS2 sub-scores | 1.000 |

The three derived features (`NEWS2_Total`, `NEWS2_Max_Component`,
`NEWS2_Abnormal_Count`) are computed from the same eight inputs at serving
time by the same code that computed them at training time (`features.py`), so
this is feature engineering, not leakage. `test_serving_path_matches_the_training_path`
exists to keep it that way.

Treat the accuracy as evidence that the pipeline is wired up correctly, not
as evidence that the model would generalise to real patients.

### Serving

```bash
cd backend && uvicorn main:app --host 0.0.0.0 --port 8000
```

`--host 0.0.0.0` matters: a real iPhone needs to reach your Mac over Wi-Fi.
Interactive docs at <http://localhost:8000/docs>.

```bash
curl -X POST localhost:8000/predict -H 'content-type: application/json' -d '{
  "respiratory_rate": 28, "oxygen_saturation": 91, "heart_rate": 132,
  "temperature": 38.9, "systolic_bp": 88, "consciousness": "V", "on_oxygen": true
}'
```

```jsonc
{
  "risk_level": "High",
  "confidence": 0.9999,
  "probabilities": { "Normal": 0.0000, "Low": 0.0000, "Medium": 0.0000, "High": 0.9999 },
  "news2_total": 18,
  "has_red_score": true,
  "risk_factors": [ /* all seven vitals, most concerning first */ ],
  "top_factors": ["Consciousness: Responds to voice", "Heart rate: 132 bpm", "..."],
  "recommendation": "Emergency response. Continuous monitoring and immediate assessment…"
}
```

| Endpoint | |
|---|---|
| `POST /predict` | Score one reading |
| `POST /predict/batch` | Up to 500 at once |
| `GET /model` | Model card: what was trained, on what, how well |
| `GET /health` | Liveness |

Only the four vitals an Apple Watch can measure are required. The other four
carry clinically normal defaults so a watch-only payload still scores.

### Risk factors, not just a label

A gradient-boosted tree cannot tell a nurse *why*. NEWS2 can, so it runs
alongside the model purely as the explainability layer: one sub-score per
vital, sorted by severity, each with a plain-English note. That is what the
apps render.

```bash
cd backend && pytest -q     # 11 tests
```

The tests check the things that would actually break: that deteriorating
vitals never score *lower* (monotonicity), that SpO₂ scale 2 tolerates a
lower saturation than scale 1, that probabilities form a distribution, and
that real dataset rows pushed through the HTTP API land on their own labels.

## 2. The apps

```bash
open app/VitalSense.xcodeproj
```

Two targets, one shared source folder:

```
app/
├── Shared/              compiled into both targets
│   ├── VitalsReading.swift      the reading, and where each number came from
│   ├── RiskPrediction.swift     the decoded /predict response
│   ├── RiskAPIClient.swift      URLSession client
│   ├── RiskPalette.swift        the four risk colours
│   ├── ConnectivityPayload.swift  watch ⇄ phone wire format
│   └── AppSettings.swift
├── VitalSenseWatch/     watchOS 11+
└── VitalSense/          iOS 18+
```

The project is generated, not hand-maintained — add a `.swift` file to a
target folder and re-run:

```bash
python3 app/tools/generate_xcodeproj.py
```

### Checking it works without a wrist

The Swift in `Shared/` normally needs a simulator, a paired watch and a
signing identity to run at all. `tools/check_client.sh` compiles those same
source files for macOS and drives them against a live server, so the JSON
contract between Swift and FastAPI is verified on every change:

```bash
cd backend && uvicorn main:app --port 8000 &
app/tools/check_client.sh
```

It checks that a healthy watch-only reading comes back `Normal` with a NEWS2
of 0, that a deteriorating one comes back `High` with the red-score flag,
that all seven factors decode and stay sorted by severity, that
probabilities form a distribution in clinical order, that FastAPI's
fractional-second timestamps parse, and that an unreachable server produces a
readable error rather than a hang.

`--seed-simulator` additionally pushes a three-reading history into a booted
iOS Simulator, so the results screens render with real model output before
any watch is involved.

## Running it on your own devices

Everything below assumes you cloned the repo and have Xcode installed.

### 1. Start the model server

The apps are useless without it — they send vitals somewhere to be scored.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
cd backend && uvicorn main:app --host 0.0.0.0 --port 8000
```

The trained model is committed, so there is nothing to retrain. `--host 0.0.0.0`
is required: bound to localhost, your phone cannot see it.

**Either everyone runs their own server, or one person runs it and the rest
point at their Mac.** Both work — it is one address in the app's Settings
screen. Whoever hosts finds their address with `ipconfig getifaddr en0` and
shares `http://THAT-ADDRESS:8000`. Everyone must be on the same Wi-Fi, and
many corporate or guest networks block device-to-device traffic entirely; a
personal hotspot is the reliable fallback.

Sanity check from the phone's browser before touching Xcode:
`http://THAT-ADDRESS:8000/health` should return `{"status":"ok",...}`.

### 2. Make the project yours to sign

Bundle IDs are globally unique to Apple, so two people cannot both ship
`com.bayhacks.VitalSense`. In Xcode, for **each** of the two targets →
Signing & Capabilities:

- Tick **Automatically manage signing** and pick your Team (a free Apple ID is fine)
- iOS target bundle ID → `com.yourname.VitalSense`
- Watch target bundle ID → `com.yourname.VitalSense.watchkitapp`

The watch ID must be the iOS ID plus `.watchkitapp`, or the watch app will
not install. Then edit `app/VitalSenseWatch/Info.plist` and set
`WKCompanionAppBundleIdentifier` to your new iOS bundle ID — that one is not
automatic.

Add the **HealthKit** capability to the *watch* target only (+ Capability →
HealthKit). The iPhone app never touches HealthKit.

> These edits are personal to your machine. Please don't commit them to
> `main` — they would break everyone else's signing. `git update-index
> --skip-worktree app/VitalSense.xcodeproj/project.pbxproj` after you have
> them set is the easy way to stop them showing up in `git status`.

> Re-running `tools/generate_xcodeproj.py` rebuilds the project from
> scratch and **wipes your signing settings and the HealthKit entitlement**.
> Only run it if you add new Swift files.

### 3. Trust the hardware

- iPhone: connect by USB, unlock, tap **Trust**. Then Settings → Privacy &
  Security → **Developer Mode** → on (the phone reboots).
- Apple Watch: Settings → Privacy & Security → Developer Mode → on, reboot,
  and keep it unlocked on your wrist.

### 4. Build

Scheme **VitalSense** → your iPhone as destination → ⌘R. The watch app is
embedded in the iPhone app and installs with it; if it does not appear within
a minute, iPhone → Watch app → VitalSense → **Install**.

In the app: **Settings → Risk server** → the address from step 1 → **Save and
test**. You want "Reachable". Then on the watch: Controls → **Start
monitoring**, grant Health access, then Result → **Read & Score**.

### What to expect on a real wrist

Probably "3 of 4 measured", with blood oxygen showing *Assumed normal*. That
is not a bug — see the sensor table above. Respiratory rate and wrist
temperature are sleep-derived, so a watch you only put on this morning has
neither yet. The watch's Controls page has demo readings that exercise the
real pipeline end to end if you need to show the whole thing working
immediately.

### What the watch can actually measure

This is the part that shapes the whole design. An Apple Watch Series 9
(A2984) covers four of NEWS2's seven vitals, each on its own schedule:

| Vital | Availability |
|---|---|
| Heart rate | Continuous. The app starts an `HKWorkoutSession` to raise sampling from every few minutes to roughly 1 Hz |
| Blood oxygen | Background sampling at rest — **and disabled outright on units sold in the US after January 2024** |
| Respiratory rate | Derived during sleep only |
| Wrist temperature | Derived during sleep only |
| Systolic BP | Not measurable by any Apple Watch |
| Consciousness (ACVPU) | Not measurable |
| Supplemental oxygen | Not measurable |

So the apps never pretend. Every vital carries a **provenance** —
`sensor`, `manual`, or `assumed` — and the iPhone shows it: "3 of 4
measured", "Assumed normal: blood oxygen", "Measured 4 minutes ago". A
"Normal" verdict built on four assumptions is visibly that.

The three unmeasurable vitals live on the iPhone's **Other vitals** sheet.
Blood pressure matters most — a systolic under 90 is three points on its own
— so leaving it silently at 120 would flatter every reading. Changing
anything there re-scores the latest reading and pushes the new result back to
the watch.

### Wrist temperature is not body temperature

`appleSleepingWristTemperature` is skin temperature at the wrist: roughly
33–35 °C in a healthy person. Fed straight into NEWS2 that scores 3 points
for hypothermia on someone who is perfectly well. Apple's own Health app
never shows the absolute value either — it shows a *deviation* from your
personal baseline.

So `VitalsCollector.estimatedBodyTemperature()`:

1. Uses a real `bodyTemperature` sample if one was logged in the last 12 hours.
2. Otherwise averages the last 30 days of wrist readings into a baseline,
   takes tonight's deviation from it (clamped to ±3 °C, because a wider swing
   is a loose band or a cold room), and applies that to a normal 37.0 °C.
3. With fewer than three nights of data, returns nothing — the reading keeps
   its assumed value and is flagged `assumed` rather than inventing a fever.

### How a reading travels

```
Apple Watch                    iPhone                     FastAPI
  sensors ──► reading ──WC──►  + manual vitals ──HTTP──►  /predict
                               ◄── prediction ◄──────────
  band ◄──────────────────────  reply
```

`WCSession.sendMessage` carries the reading and the reply carries the
prediction, so the watch gets its answer in one round trip. If the phone is
out of range the watch calls the API itself — the phone pushes the server
address down via `updateApplicationContext` so the fallback points somewhere
real — and queues the reading with `transferUserInfo` so the phone's history
fills in later.

### On screen

**iPhone** — three tabs. *Now* answers three questions in order: the verdict
(band, NEWS2 total, recommendation), what the watch actually measured (four
tiles with provenance), and what is driving it (contributing vitals with
severity and points), then the model's confidence across all four bands.
*History* keeps the last 100 readings, including ones that failed to score,
with the reason. *Settings* holds the server address with a reachability
test, the watch link state, and a demo button.

**Watch** — three vertical pages: the result as a hero readout, the live
vitals with their provenance, and controls (start/stop monitoring, plus demo
readings). No chart; the screen is too small for one to be honest.

### No watch? No problem

Both apps have a demo path that runs a plausible reading through the real
pipeline — real `WCSession` on the watch, real HTTP call, real model. iOS:
Settings → *Score a demo reading*, or the button on the empty state. watchOS:
the Controls page. Demo readings are tagged `source: "demo"` so nothing
downstream mistakes them for measurements.

### Colour

The four bands use a reserved status palette — good, warning, serious,
critical — that never doubles as a series colour. Two of the four sit below
3:1 contrast on a light surface by design, so the mitigation is structural:
a band never appears without its SF Symbol **and** its written name, and
every severity is spelled out ("Moderate · 2 points") next to its colour.
Colour alone never carries meaning anywhere in either app.
